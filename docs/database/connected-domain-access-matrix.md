## Evidence and boundaries

Authoritative definitions are [`schema.prisma`](../../packages/database/prisma/schema.prisma) and [`202610060001_connected_domains/migration.sql`](../../packages/database/prisma/migrations/202610060001_connected_domains/migration.sql). - **29 original application tables are retained; 16 new tables bring the inventory to 45.** Provider Auth/storage and `_prisma_migrations` are outside that count. The seven historical migrations remain untouched by this documentation task; the eighth is the connected-domain migration.
- The new migration is transactional (`BEGIN`/`COMMIT`). Its strict ACL closure covers **only the 16 new tables and 14 new trigger functions**, not every existing application object. New-table RLS is enabled, with **no policies, no FORCE RLS, and no backend/runtime grants**. PUBLIC/browser table, column and function privileges are revoked on the allowlisted new objects; unexpected non-owner grants or unsafe browser authority cause failure rather than broad cleanup.
- Existing table/column grants and existing-table RLS policies are preserved, including `notifications`, `rewards_redemptions` and `rewards_transactions`. Existing table privileges cover newly added columns. Source lockdown is not proof that a hosted legacy column, view, RPC or inherited role path is safe.
- The current application ACL preflight independently lists **all 45 tables**, consistent with the new SQL's deployment-gate comment.
- New metadata, relations, enums and generated model types may compile without implementing a feature. Compilation, catalog parity and successful migration deployment are separate from API authorization, storage acceptance and runtime acceptance. Actual local build and regression results are recorded in [validation results](connected-domain-validation.md), not inferred from this access matrix.

A future grant review must be **operation- and column-specific**: bounded SELECT projections, INSERT only for approved append-only records, UPDATE only for mutable approved fields, and DELETE only for approved non-evidence operations such as a bookmark. Do not issue blanket CRUD, TRUNCATE, REFERENCES, TRIGGER, schema CREATE, grant options, role-management powers or ledger write privileges to runtime/browser identities. Include the SELECT and locking privileges needed by trigger parent lookups; `FOR UPDATE`/`FOR SHARE` can require UPDATE authority even where no row change is intended. That tradeoff needs review and tests, not a blanket grant recommendation.

### Critical invoker/RLS limitation: not solved by an all-row policy

All 14 new functions are `SECURITY INVOKER`, with pinned `search_path = pg_catalog, pg_temp`. Parent lookups run under the caller's privileges/visibility; missing or hidden evidence may fail closed. Three guards specifically check `row_security_active`:

- `connected_certificate_event` rejects event-history validation when RLS is active on `certificate_events` (`42501`), even with a non-owner policy that permits all rows. Event writes also require SERIALIZABLE (`25000` otherwise), with future callers handling `40001` retries.
- `connected_service_event` similarly rejects active RLS on `service_request_events` (`42501`).
- **`connected_protect_linked_debit` affects the existing `rewards_transactions` table.** Changes to `id`, `customer_id`, `rewards_account_id`, `transaction_type`, `reversal_of_id`, `amount`, or a changed status outside POSTED/REVERSED enter its scope-sensitive check. If `row_security_active('public.rewards_redemptions')` is true, the operation fails with `42501` **before checking whether a linked redemption exists**. With inactive RLS and an actual link, mutation fails with `23514`. Consequently, even an all-row non-owner redemption policy does not make these existing debit updates work; potentially unlinked rows can also hit the visibility rejection. This is a regression/compatibility gate, not a promise of working legacy rewards CRUD.

The scoped benefit/account FKs provide separate referential protection and do not remove these guard limitations. Granting SELECT, adding `USING (true)`, or passing an ACL preflight does not make `row_security_active` false. **Do not recommend a superuser, owner, BYPASSRLS login, disabling RLS, or disabling triggers to make runtime tests pass.** Database/security/backend owners must approve a separately reviewed design change or explicitly keep the affected operations unavailable, then validate with the intended real non-owner runtime role.

## Field, history and operational exposure

- **Evidence storage:** `storage_bucket`/`storage_object` identify private objects, not public or signed URLs. Restrict these identifiers, checksums, uploader/reviewer IDs and internal notes in DTOs. No inline document contents, credentials, raw verification tokens or signed URLs belong in business rows, routine logs or browser list projections.
- **Identity:** requested names, birth date, nationality and address are sensitive PII, not a general JSON override. Correction fields do not include email/mobile/RHC ID/status overrides. Audit before/after JSON and integration payloads can also contain sensitive data; absence of a typed PII column does not make them public.
- **History operations:** `document_versions`, `document_reviews`, `payment_records`, `payment_record_events`, `certificates`, `certificate_events`, `service_request_events` prohibit UPDATE/DELETE and TRUNCATE. Guards are ENABLE ALWAYS and have no caller/session bypass. Identity requests, checklist evidence/completion and benefit-linked redemption snapshots have additional retention guards. New no-TRUNCATE protection also covers `identity_review_requests`, `turnover_checklist_items`, and existing `rewards_redemptions`.
- **Maintenance:** runtime must not own tables, change functions/triggers, control replication/session suppression, or edit `_prisma_migrations`. Backups, legal erasure/anonymization and exceptional evidence repair require separate operator procedures; do not weaken integrity constraints to implement ordinary delete endpoints.
- **Functions/views/RPC:** the 14 trigger functions are internal enforcement, not callable API features. Caller EXECUTE is not needed for normal trigger firing; do not grant it as a workaround. Review indirect views, SECURITY DEFINER functions and inherited function EXECUTE/defaults independently. No migration helper or generic SQL RPC should be exposed to browsers.
- **Metadata ≠ capability:** certificate issuer FK, service assignee FK, publication timestamps, document metadata and benefit approval fields compile as data structures, but do not prove issuer authority, staff eligibility, public disclosure, storage operation or benefit activation.

## Approval and evidence checklist

Every item is **pending target-specific approval/validation** unless supported by a separately recorded result:

1. Database/change owner reconciles the same-name historical migration checksum described in the integration report; accepts schema + eight-migration manifest and backup/recovery scope. Never automatically resolve the ledger.
2. Database/security owners sign off actual creator, owner, browser, catalog-review and candidate runtime roles, membership paths, defaults, table/column/sequence ACLs, views and RPCs. Both verifier and 45-table ACL preflight need review; missing browser roles are not a pass.
3. Backend/security owners resolve or explicitly block invoker/RLS-incompatible operations, including **existing rewards debit updates**. Test approved runtime positively and test cross-customer/company/project denial; owner fixture success is insufficient.
4. Domain owners approve the proposed enums/lifecycles, field semantics, permissions, review/issuance/assignment/publication authority and retention. New capability gates remain unavailable until implementations and acceptance exist.
5. Privacy/storage owners approve a **separate private-storage plan**: private buckets, object naming, no overwrite/deletion of retained evidence, upload scanning/hash/MIME validation, short-lived scoped download authorization, retention and recovery. **No buckets, storage policies or objects were modified here.**
6. Release owner records catalog results, unresolved CHECK deparser differences, migration/upgrade evidence, runtime and API acceptance separately. Offline schema/tool checks are not evidence of a clean hosted catalog or working product.
