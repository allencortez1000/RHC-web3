# Connected-domain source map

**Snapshot: 2026-10-06. Scope: 45 Prisma application models — 29 existing + 16 connected-domain additions.**

These three documents are the authoritative connected-domain **design/source documentation until the next reviewed design update**: this source map, the [data dictionary](connected-domain-data-dictionary.md), and the editable [ERD](connected-domain-erd.md). Executable schema and SQL remain authoritative for exact definitions. This is not business approval, migration authorization, deployment evidence, or an API activation announcement. If sources change, update the documents together; do not resolve a conflict by assuming a proposal was approved.

## API and demo translation boundaries

- K blocks API-mode document/payment/certificate/service-request endpoints for both `me` and `admin`, customer identity-review/saved-properties/rewards/activity/receipts, admin rewards-ledger and notification read mutations. The demo implements synthetic behavior independently. A table's existence does not remove those gates.
- Existing `/me/rhc-id`, `/business-services`, and `/admin/users/:id/verification/approve` are real controller routes, not newly unavailable merely because related new workflows are unfinished. The existing approval action updates user/profile business verification with audit evidence; it does **not** consume `identity_review_requests` or apply typed corrections. Email confirmation remains separate from business verification.
- Payment demo statuses (`SUBMITTED`, `PENDING`, `POSTED`, `REVERSED`) are not a production `PaymentRecord.status` enum. S/M use `SUBMITTED`, `VERIFIED`, `REJECTED`, `REVERSED`, `NOTE` **event types**. A future API must define its status projection and mappings; do not rename VERIFIED to settlement POSTED by assumption.
- Certificate demo statuses and blockchain labels are view data. S/M store no certificate status, issued-at, raw public reference, blockchain status or generic linked-record column. Pending derives from no issuance; lifecycle derives from events and expiry. Digital ID still lives in `user_profiles`, not automatically a certificate.
- Demo service progress uses `SUBMITTED` and `ACKNOWLEDGED`; S/M propose `PENDING`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`, `REJECTED`. This is a deliberate unresolved contract mismatch, not exact parity.
- Demo document content/issuer/version rows must be mapped into private-object versions and version-specific reviews; do not copy synthetic plaintext content into production business tables. Demo revision counters, world/session/control records, receipts and frontend aggregates do not imply extra tables.
- Demo integer minor units and points need explicit exact-decimal serialization/conversion contracts. JavaScript floating-point conversion is not an approved money/ledger convention.

## Extensions and deployment constraints

The final source inventory contains **45 models, 472 scalar/enum columns (186 on the 16 new tables), and 96 owning-side FK relations**. Turnover adds two nullable UUID actor fields with no defaults: `created_by_id` and `responsible_user_id`. Both have User FKs with RESTRICT delete/update actions and their own nonunique indexes. User inverse relations are `created_turnover_cases` and `responsible_turnover_cases`; these add no User columns. SQL freezes the creator value from insertion, including NULL, while responsibility remains mutable. Neither actor is inferred or assigned automatically, and FK existence does not establish staff authority.

M adds six columns on existing tables: `notifications.read_at`; `rewards_redemptions.benefit_id`, `benefit_company_id`, `accepted_points_cost`, `accepted_terms_snapshot`, `original_debit_id`. The nullable company snapshot is DB-derived from the benefit; composite FKs to both `rewards_accounts(id, company_id)` and `rewards_benefits(id, company_id)` protect scoped links against later reparenting, including account company NULLing. M adds candidate keys on existing `reservations(id, customer_id, property_id)`, `business_services(id, company_id)` and `rewards_accounts(id, company_id)`, plus a candidate key on new `rewards_benefits(id, company_id)`, a redemption scoped-account index and debit-retention guards. Inverse Prisma relation arrays do not add columns. Reservations gain **no** idempotency column, revision column or new transition behavior. Profiles gain no correction override.

The 16 new tables have **23 UTC transaction-time `dbgenerated` defaults**. Seven new mutable tables have an alphabetically early BEFORE INSERT/UPDATE trigger that replaces `updated_at` with database UTC wall time before guards, overriding client clock skew. Supplied factual creation/submission/decision timestamps are preserved and validated against UTC; existing timestamp defaults/rows are not converted. New or changed non-NULL notification `read_at` is stamped with UTC wall time; NULL and unchanged values remain untouched. Milestone ID/project/code/creation are frozen. M defines **14 trigger functions**; full semantics and current counts are in the dictionary.

M wraps changes in a transaction. Its strict table/column ACL and RLS closure covers **only the 16 NEW tables**; its function ACL allowlist covers all 14 new trigger functions. It revokes PUBLIC/browser rights on those objects and rejects unexpected non-owner ACLs or unsafe browser memberships. **Existing table/column grants, including notifications and rewards_redemptions, are preserved**; this migration does not reapply legacy browser revocations or alter existing-table RLS policy. Existing table grants cover added columns, so the now-expanded **45-table preflight must still assess actual effective privileges before deployment**. New-only lockdown is not assurance about legacy exposure.

M supplies no backend grant, new RLS policy, role topology or FORCE-RLS contract. Owners/superusers can bypass RLS; this is not runtime authorization. SECURITY INVOKER guards require parent visibility and some reject filtered history outright. New connected-domain runtime remains blocked pending a role/ownership/authorization decision, without revoking legitimate existing backend grants. Trigger retention has no caller/session bypass, but separately authorized DDL could change it; runtime roles must not receive DDL authority.

## Open design/source gaps — explicit handoff

1. **Deployment/security:** P now lists all 45 tables; the expansion gap is resolved in source. Actual role memberships/default ACLs, existing-table/new-column exposure, views/RPCs and trigger visibility still need target preflight and approval. Unexpected grants on NEW tables/functions can make M roll back; existing notifications/redemptions grants are deliberately preserved. Do not bypass checks or assume a service role is approved.
2. **Business lifecycle approval:** all 11 new enum definitions are proposals. Approve legal transitions, permission codes, issuer authority, delegation, assignee eligibility and publication rules. Service progress is not a fully enforced business transition graph, nor is turnover.
3. **Identity evidence/corrections:** single optional evidence is provisional. No multi-evidence join, field-clear marker or atomic approved-profile application workflow exists. NULL means “not requested,” not “erase.” Typed changes exclude email/mobile/RHC ID/status. Reviewed state alone never updates/unlocks profiles.
4. **Projection consistency:** service header status/assignee and document header status are not automatically synchronized with history; a future API must lock and update consistently. SQL does not require every payment header to have a SUBMITTED event or every service header a CREATED event. Retry uniqueness alone does not compare repeated request payloads.
5. **Evidence/content trust:** checks validate metadata syntax and cross-row identity, not actual object bytes, MIME authenticity, malware scanning, reviewer legal authority, document approval as a prerequisite for every downstream use, or customer entitlement to a referenced property. Private storage immutability/retention and policy approval remain independent.
6. **Verification:** hashes are not public response contracts. Current certificate-target references may point to pending artifacts; profile issuance is checked at reference write, not continuously. Future verification must recheck current validity/revocation/consent and approved disclosure. Hard-disabled SQL must be changed through separate approval.
7. **Rewards:** hard-inactive benefits do not by themselves prevent a privileged writer from inserting a benefit-linked redemption. No overspend prevention, balance posting engine, approved prices/terms, activation eligibility, or automatic debit creation is supplied. Debit matching uses absolute amount to avoid inventing historical ledger sign conventions. The DB-derived `benefit_company_id` snapshot and two composite FKs now protect scoped benefit/account links against later company changes, including NULLing, without imposing that new blocker on unlinked legacy accounts or global benefits. These consistency guarantees do not supply approved eligibility or a posting engine.
8. **Turnover/milestones:** multiple cases per pair remain possible, and case completion does not automatically require all required checklist items. Completion evidence is optional. Optional creator/responsible-user fields are proposals, not approved assignments; the future API must authenticate creation attribution and authorize responsibility changes. SQL retains no dedicated responsibility-change event history and does not infer an actor. An initially NULL creator cannot later be filled in through ordinary UPDATE. Milestone progress and publication need approved audience/permission policy; date/check constraints are not publication authorization.
9. **History and retention:** append-only guards conflict intentionally with ordinary hard deletion. Approve legal retention, deletion/anonymization, backups and controlled maintenance. Some mutable headers/config records have no dedicated historical event model. Millisecond timestamps are not a universal total order; only service events have an explicit sequence.
10. **Operational acceptance:** no live migration, concurrency, ACL, RLS, storage, endpoint or integration acceptance is established. Certificate event writes now **require SERIALIZABLE in SQL** (25000 otherwise); callers must retry serialization failures (40001). SERIALIZABLE with retries is also recommended for other new cross-row lifecycle APIs, but only certificate events impose that isolation check. Same-property/same-logical-document supersession is a conservative enforced proposal; cross-source/source-kind replacement needs separate approval. Acceptance tests remain future work, not results. New defaults/guards use UTC while legacy timestamps are not converted; validate legacy chronology and API date serialization before rollout.
11. **Documentation drift:** R's “not implemented schema” and A's historical migration count predate S/M. They are useful lineage, not current inventories. M and P now both describe the 45-table preflight inventory. Historical documents remain evidence of their earlier snapshots, not of this uncommitted implementation.

Provider-managed Auth/storage and Prisma bookkeeping are excluded from 45. Optional outbox, webhook, delivery, consent-policy and shared idempotency tables remain separate design choices. No wallet custody, private keys, blockchain transaction tables, payment gateway, invoicing or settlement ledger is introduced.
